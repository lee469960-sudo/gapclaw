## Context

现有 `AgentTick` 由 API 启动时的进程内 APScheduler 装载并直接调用 Agent。它没有执行台账、跨副本排他权或恢复协议，并且遗留任务写接口与会话路由形成两条不同的调度路径。详见 [proposal.md](proposal.md)；行为契约见 `specs/session-scheduled-tasks` 与 `specs/channels`。

## Goals / Non-Goals

**Goals:**

- 在 SQLite 开发环境和 PostgreSQL 生产环境中安全领取和执行会话任务。
- 使每个触发实例、Agent 运行和通知投递均可追溯、可恢复、可显示。
- 不改变普通聊天、非定时 Agent、未绑定 Skill/MCP 或未配置渠道时的行为。

**Non-Goals:**

- 不提供任意脚本/HTTP webhook 调度，也不提供跨会话任务。
- 不将模型对业务语义的自我判断作为自动成功判据。
- 不承诺对不可幂等的外部 MCP 副作用实现跨系统 exactly-once；执行器只保证不会重复启动同一已领取实例。

## Decisions

### 数据模型以任务、执行和投递分层

保留并演进现有任务配置，新增 `scheduled_task_runs` 与 `scheduled_task_notification_deliveries`。任务保存会话、Agent、所有者、调度类型及参数、时区、`next_run_at`、启用/软删除状态、可选运行时快照和通知设置；执行保存唯一 occurrence key、状态、租约、尝试、时间戳、错误、关联 Agent run/message 与配置版本；投递保存独立幂等键、状态和重试信息。

任务配置与执行记录分离，使修改未来计划不会篡改历史。通知也与执行分离，防止渠道重试重复触发 Agent。替代方案是只扩展 `AgentTick` 并记日志；它无法表达多个尝试、通知状态和可见历史。

### 数据库为调度权威，Worker 不持有唯一状态

新增独立 Scheduler Worker，它周期性计算到期/补跑实例并以唯一 occurrence key 创建执行记录。Worker 通过带有效期的租约原子领取 `pending` 实例；PostgreSQL 使用行锁/跳锁，SQLite 使用条件更新和短事务。仅成功领取者调用会话运行时，租约到期实例由后续 Worker 回收。任务与 `scheduled_for` 的唯一约束抵抗多副本扫描和重复补跑。

这优于每个 API 副本各自加载 APScheduler。租约意味着崩溃后可能需要恢复同一实例，因此 Agent 入口还必须在启动前检查执行实例状态并将关联 run/message 原子记录；无法证明外部副作用幂等时记录该风险并不自动重复业务失败。

### 会话是串行执行域

Worker 领取运行前取得会话执行槽；同一会话的自动任务按 `scheduled_for` 与创建序排序。无槽的实例保留 `pending`，到达最大排队时长转为 `failed` 并写回可见说明。手动立即执行与正式实例完全共用此队列。

并行执行虽然提高吞吐，但会互相污染会话上下文、文件和工具副作用；直接跳过又违背补跑和可见性目标。

### 会话运行时复用与成功边界

Worker 通过既有的正式会话 Agent 入口构造带来源元数据的触发消息，而非另起无状态 Agent。默认每次读取当前会话配置；若任务开启快照，则读取任务创建时持久化的脱敏配置。运行完成、结果消息持久化且执行记录关联该消息后才标记成功。基础设施错误按三次指数退避；Agent 的业务失败、人工取消和不可恢复运行时错误不自动重跑。

这保留 Agent、普通对话、已绑定工具与断点恢复的既有语义；触发元数据需避免作为普通用户输入改变模型路由或泄漏凭据。

### 跨进程取消边界

定时任务的停止不能复用 API 进程内的 `stop_chat` 状态，因为执行器在独立 Worker 进程。执行记录保存持久化取消请求；授权停止操作会停用任务、取消 pending 实例，并在当前 running 实例存在时写入该请求。Worker 将该请求接入正式 Agent 运行时的取消检查，在下一次可取消边界终止执行，将实例置为 `cancelled` 并释放会话槽。取消不绑定成功消息、不创建通知 outbox，也不进入基础设施重试；已经发生的外部 MCP 副作用仍不能回滚，必须在执行历史中保留此限制。

### API 和前端收敛于会话资源

所有读写使用会话范围路由，并通过统一授权帮助函数检查用户、Agent、会话、任务所有权和协作者编辑权。旧 Tick 写端点在迁移后拒绝写入，兼容期仅返回映射后的只读结果。前端以同一 API 展示配置、时区搜索、下次运行与执行/通知历史。

### 渠道通知采用独立 outbox

执行成功写回会话后创建通知 outbox 记录；一个投递 Worker 以独立有限重试发送。投递失败不修改任务执行成功状态，最终失败写入会话告警。未配置渠道时不创建投递，普通会话行为不受影响。

## Risks / Trade-offs

### 定时任务跨进程进度

现有 hub 仅在进程内分发事件。定时 Worker 在调用正式运行时期间订阅本会话步骤并保存每个 Run 的进度快照；API 使用会话权限校验读取，前端会话内定期读取真实步骤，刷新后恢复，结束时刷新消息。进度展示不调用模型或工具，不改变 MCP 重试/缓存。新表为增量兼容变更，回滚代码可保留表。空白触发在配置和执行入口拦截，空白结果不标记成功。

- [SQLite 并发写锁与长运行竞争] → 使用短领取事务、条件更新、开发环境单 Worker 建议及 SQLite 并发回归测试。
- [租约崩溃恢复可能遇到外部 MCP 已产生副作用] → occurrence key、运行前状态检查、只重试基础设施错误，并把外部副作用风险记录为已知限制。
- [运行时配置变化造成行为漂移] → 默认记录实际版本，提供显式快照模式。
- [旧/新执行器重叠导致双跑] → 功能开关控制唯一执行者，灰度期新 Worker 只做 shadow 计划核对。
- [IM 不可用掩盖结果] → 会话回写是成功前提，通知独立可见告警。
- [跨进程取消不能回滚外部副作用] → 取消请求只阻止后续运行时步骤并终止本地 Agent；保留 run/lease 审计，禁止将取消自动重试。

## Migration Plan

1. 发布数据库迁移、只读查询能力和关闭状态下的新 Worker，不改变现有 Tick 的执行权。
2. 迁移可归属的旧任务，默认 `Asia/Shanghai`；禁用无法归属记录并写入迁移原因。
3. 在管理员/测试工作区启用 shadow Worker，比较下次运行、领取和迁移结果，但不启动 Agent。
4. 以功能开关按工作区灰度移交执行权；同一任务任一时刻仅一个执行器启用。
5. 监控重复 occurrence、任务延迟、租约回收、队列深度、补跑、执行和投递失败率后全量启用。
6. 回滚时关闭新 Worker 并恢复旧执行器；保留新配置与历史，且仅在确认无重叠实例后恢复旧任务执行。
