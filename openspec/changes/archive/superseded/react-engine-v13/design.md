# Design — react-engine-v13

## Context

动机与根因见 `proposal.md`「Why」。两条主线：收敛（R1/R2，治「小任务空转」）与计划智能（R3，治「视图匹配不贴切」）。

**铁律松口（用户已拍板）**：R1 引入「无进展软预算」——一个静态的无进展计数器。这是对「无任何静态硬门禁」的**显式、限定范围的放宽**：仅此一个计数器，且动作是 LLM 生成的诚实总结（复用 `_distill_final`），不是粗暴截断；只在「持续无进展」时触发，不切断仍在推进的任务。R2/R3 不新增任何门禁。

## Goals / Non-Goals

**Goals:**
- 小任务不再空转到 `max_iters`：无进展时提前用诚实总结收尾。
- 短任务少交一轮「精准税」：无交付物的 FINAL 跳过复核。
- 具体需求能一步匹配候选视图：视图名清单 + 字段/口径映射注入 PLAN。

**Non-Goals:**
- 不加任何「仍在推进就截断」的硬停（R1 只针对无进展）。
- 不改 MCP / Skill 内容（视图目录机制在引擎侧，靠缓存 MCP 返回）。
- 不改 group failover / 退避重试（v10/v11 已定）。

## Decisions

### D1: 无进展软预算（铁律限定放宽）

新增 `state.no_progress_streak`：一轮里「无工具执行成功、无文件写入、无进度新增、无子任务推进」则 +1，任何推进则清零。达到阈值（默认 5）→ 复用 `_distill_final` 生成诚实总结收尾（明确标注已做/缺口），`_clear_run_state` 后返回。
- **为何**：把「按轮数预算（max_iters）」升级为「按无进展预算」，只收拾已经卡死的小任务，不切断有进展的任务。
- **边界**：这是唯一的静态门禁，且收尾内容由 LLM 生成（诚实、可读），非截断。

### D2: 短任务跳过 `_reflect_final`

FINAL 分支判断：若 `state.subtasks` 为空（无多子任务 PLAN）且 `saved_paths` / `files_written` 为空（无交付物）→ 跳过 `_reflect_final`，直接 `state.final = candidate` 收尾；否则仍走 Verifier。
- **为何**：短任务（读文件、答简单问题）无实质交付物可核，PASS 几乎必然，复核只白花一轮；有交付物/多子任务才值得核数字/SQL/口径。

### D3: 视图目录缓存 + 注入

缓存 MCP `list_ads_views` 的视图名清单（跨会话，按 MCP id 或 agent 级），连同本次/历史蒸馏出的 `view→字段/口径` 映射，注入 task_context（PLAN 阶段可见）。
- **为何**：让 PLAN 有据可查地一步语义匹配候选视图，describe 只确认 top 候选，根治「逐个 describe 60 个视图」。

### D4: 铁律其余不变

除 R1 的「无进展软预算」外，不新增任何循环级阈值 / 计数器 / 硬停。

## Risks / Trade-offs

- [风险] R1 无进展阈值 5 太小会误杀「慢但没失败」的任务。→ 缓解：推进信号宽口径（工具成功、写文件、进度、子任务推进都算推进）；阈值温和；收尾是 LLM 诚实总结、明确标注缺口，用户可续。
- [风险] R2 跳过复核可能放过短任务的错误答案。→ 缓解：短任务无交付物、答案易判，风险低；一旦有交付物仍复核。
- [风险] R3 视图目录缓存可能过期（schema_ads.yml 变了）。→ 缓解：缓存带 TTL / 失效策略；describe 命中候选仍会确认字段，兜底过期。

## Open Questions

- R1 无进展阈值具体取值（默认 5）与推进信号的宽口径界定。
- R3 视图目录缓存的落点（MCP 级 vs agent 级）与 TTL。
- R3 是否需要「视图语义描述」的来源（当前只有视图名，无一句话语义；语义描述若要，需从 MCP/skill 侧补）。
