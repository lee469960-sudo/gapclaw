## Context

当前 Agent Runtime 将普通请求送入无工具的 conversational fast path。该路径只有空文本/调用失败 fallback，不检查复杂问题是否被完整回答；而 React Engine 负责工具任务，不能为了格式强行加载 MCP。方案必须在两者之间增加轻量质量层，并与已有模式预算、能力路由和人工确认保持兼容。

## Goals / Non-Goals

**Goals:**

- 在不增加简单闲聊延迟的前提下识别复杂普通问题。
- 支持 Agent 级别的回复风格，默认兼容既有 Agent。
- 对明显不足的复杂回复执行一次可观测、可终止的补全。
- 让得到大脑等内容型 Agent 能稳定输出摘要、要点和说明。

**Non-Goals:**

- 不把所有普通对话改造成 React Engine 任务。
- 不让质量检查自动连接 MCP、Skill 或执行工具。
- 不引入第二个长期运行的评审 Agent 或无限自我反思循环。
- 不改变生产发布、删除、权限和人工确认规则。

## Decisions

### 1. 质量检查放在 conversational path 内

复杂度判定复用执行策略的确定性信号；通过后仍进入 chat。首次回复后只对复杂请求或 `structured/analytical` 风格执行轻量检查。相比所有请求都调用评审 LLM，这样保持闲聊低延迟并避免重复推理。

### 2. 质量判断采用确定性门槛加一次 LLM 补全

确定性门槛检查回复长度、关键请求实体覆盖、是否包含用户要求的结构词，以及“我可以帮你”等未作答模式。命中后使用一次同一模型补全提示；不增加工具权限，也不要求内部 FINAL 协议。补全最多一次，终态必写入指标。

### 3. 回复风格采用 Agent 配置并向后兼容

新增风格字段默认 `adaptive`。`structured` 和 `analytical` 只改变 chat 系统提示和质量门槛，不改变任务路由；无效值安全回退，既有 API 客户端无需迁移。

### 4. 质量状态进入既有运行指标和步骤流

复用 `runtime_metrics` 与会话步骤记录 `quality_check`、`quality_retry`、原因和最终状态，内容只保存脱敏摘要。前端显示为回复质量状态，不伪装成 MCP/Shell 工具调用。

### 5. 内容型 Agent 的数据请求仍优先走任务路由

出现来源、日期、笔记、查询、提取等外部状态信号时，能力路由优先级高于 chat 质量补全；质量层不得掩盖 MCP 未绑定或工具失败。

## Risks / Trade-offs

- [风险] 复杂度门槛误判简单问题 → 仅允许一次补全，并以 `adaptive` 默认；加入问候/短事实回归。
- [风险] 补全增加模型调用成本 → 只对复杂请求或结构化风格启用，且严格一次上限。
- [风险] 模型仍输出过短结果 → 记录 `quality_incomplete`，不循环；用户可继续追问。
- [风险] 新字段与旧数据库不一致 → 使用可选字段和运行时默认值，提供兼容 API 序列化。
- [风险] 本地热重载再次丢失 done → 复用已有前端状态恢复逻辑，质量步骤必须可从历史恢复。

## Migration Plan

1. 先增加策略函数、配置默认值和单元测试，不改变默认 Agent 行为。
2. 增加 conversational 质量补全和指标，再增加前端状态展示。
3. 对得到大脑 Agent 显式设置 `structured`，观察轮次、补全率和用户反馈。
4. 若补全率或延迟异常，将风格回退为 `adaptive`，或通过策略开关关闭质量检查；保留原单轮路径。
