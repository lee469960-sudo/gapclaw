## Context

见 `proposal.md` 的 Why。当前最终回复是 `FINAL` 之后的自由文本，或预算耗尽时的收尾摘要，直接写入 `ChatMessage.content`。Web 与渠道按这段正文做 Markdown 渲染。`ChatMessage.meta` 已是 JSON 文本。执行过程用独立步骤事件，不在主气泡里。

目标契约已写在 `docs/react-engine-output.md`。本设计只决定怎么落到现有运行时，不改工具协议。

## Goals / Non-Goals

**Goals:**

- 在所有运行结束出口使用同一个归一化函数，生成六字段信封。
- 正文只存 `message`；信封放进现有 `meta`，不新增表字段。
- 进行中的模型原文不得成为主气泡正文。

**Non-Goals:**

- 不改 `FINAL`、工具行和执行过程卡片的数据结构。
- 不渲染 `actions`，不发出 `type=action`。
- 不回填历史消息的信封。

## Decisions

### 1. 归一化放在落库边界

新增一个纯函数：输入为结束原因、已接受的 `FINAL` 文本、可解析的结构摘要和进度事实；输出为信封。`runtime` 的完成、预算耗尽、用户取消、执行失败、等待用户这几条出口都调用它，然后再写助手消息。

模型不负责输出该 JSON。已接受的 `FINAL` 若已是面向用户的 Markdown，则作为 `ok` 回复的 `message`；其中的代码块可以保留。未接受的中间原文只留在执行步骤里。

备选：让模型每轮直接输出信封。这会和现有工具协议冲突，因此不采用。

### 2. 信封写入 `ChatMessage.meta.output`

`content` 继续是 `message`。`meta.output` 保存完整信封。读取时没有 `meta.output` 的旧消息只渲染 `content`。

备选：新增数据库列。回滚和旧数据迁移成本更高，第一版不采用。

### 3. 状态分类表

| 出口 | status | type | message 来源 |
|---|---|---|---|
| 接受的 FINAL，且能抽出结构字段 | `ok` | `data` | FINAL 的 Markdown |
| 接受的 FINAL 或无工具普通完成 | `ok` | `answer` | 该文本 |
| `max_iters` 或用户取消 | `partial` | `answer` | 现有收尾摘要；取消时写明已停止和进度 |
| 高风险动作等待用户授权，或引擎明确要求补充 | `need_input` | `clarify` | 现有确认说明 |
| LLM 连续失败、工具级失败导致运行结束、未绑定资源停止 | `error` | `error` | 现有人话说明 |

`data` 只从已有进度事实里取路径、数量、状态、字段名。工具 stdout 和代码原文丢弃；没有结构时为 `{}`。`actions` 恒为 `[]`。

### 4. 主气泡只在结束时写入

运行过程中不把模型增量文本写成助手正文。执行步骤事件保持原样。结束时写一条助手消息。前端若收到进行中的助手正文增量，不得用它替换主气泡。渠道发送的仍是 `content`。

未配置渠道时只写会话，不额外失败。未绑定 Skill/MCP 的停止文案进入 `message`，状态为 `error`，且不调用该资源。

## Risks / Trade-offs

- [进行中不再把流式文本写入主气泡，用户要等结束才看到回复] → 执行过程卡片继续显示步骤；这是为了挡住中间代码。
- [`partial` 摘要仍可能由模型生成，偶发带上代码块] → 归一化时去掉未闭合的围栏和大段无说明代码，只保留进度句和路径。
- [调用方漏接某一出口，仍会写入原始文本] → 助手消息写入收口到一处；测试覆盖完成、预算、取消、失败、等待用户、无工具对话。
- [旧前端忽略 `meta.output`] → 正文已是 Markdown，旧前端行为保持正确。

## Migration Plan

1. 先部署只写 `meta.output`、正文仍为 Markdown 的 API。旧前端和渠道无需同时发布。
2. 再让 Web 忽略进行中的助手正文增量。
3. 回滚：停止写入 `meta.output`，恢复结束路径直接保存原文。已写入的 `meta.output` 可留在库里，旧逻辑不读取它。不需要数据迁移。

## Open Questions

无。状态分类和存储位置已在确认的契约里定死。
